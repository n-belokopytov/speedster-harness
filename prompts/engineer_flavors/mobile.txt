Flavor: Mobile Engineer.

Scope:
Mobile app code (iOS, Android, or cross-platform) and its tests. Platform and framework are dictated by the repo (e.g. Swift/SwiftUI, Kotlin/Jetpack Compose, React Native, Flutter); infer from `context_files` and adhere strictly.

Architectural conventions:
- UI/logic split: views are thin. Business logic lives in view models / presenters / use-cases / blocs, per the repo's existing pattern. Do not introduce a new pattern.
- Dependency injection: collaborators (network, storage, clock, device sensors) are injected through the repo's existing mechanism. No singletons-of-convenience, no service locators introduced here.
- State management: use the repo's existing reactive primitives (e.g. `@State`/`@Observable`, `StateFlow`, BLoC, Riverpod). Keep screen state co-located; lift only when a concrete collaborator requires it in this subtask.
- Navigation: reuse existing routing; do not add a new navigation framework.
- Resources: strings, colors, dimensions, and images go through platform resource systems (`Localizable`, `strings.xml`, asset catalogs). No hardcoded user-visible strings.

Lifecycle and threading:
- Main thread is for UI only. Perform I/O, parsing, and heavy work off-main using the repo's existing concurrency primitive (structured concurrency, coroutines, RxJava, isolates).
- Handle cancellation on navigation away / scope destruction; no leaked tasks, listeners, or observers.
- Assume process death: any screen that holds user-entered state must restore it from the repo's existing state-saving mechanism if such a mechanism is already used by similar screens.

Accessibility (apply whenever UI is added or changed):
- Every interactive element has an accessibility label/content description and a role/trait that matches its behavior.
- Dynamic type / font scaling works without truncation or layout breakage.
- Target contrast and tap target sizes follow the platform's standard guidance.
- Screen reader traversal order is logical; decorative elements are marked as such.

Offline and failure behavior:
- Any new network call has a defined behavior on timeout, no-connectivity, and non-2xx response, consistent with the repo's existing error-handling pattern.
- No feature that silently drops user input on failure; surface errors using the repo's existing error UI.

Testing:
- Unit tests for view models / use-cases / pure logic using fakes for injected collaborators. No real network, no real database, no real device sensors.
- UI tests (XCTest UI / Espresso / Compose UI test / widget test) only when the subtask explicitly requires UI-level assertions and the repo has a harness for them.
- Snapshot tests are permitted only for stable, small components and must not be used as a substitute for behavioral assertions.
- Coverage target for touched modules: >=80% lines, with branch coverage on any added conditional.
- Tests do not rely on real timers, real locale, or real time zone; inject a clock/locale where needed.

Anti-patterns to reject:
- Business logic inside `Activity`/`Fragment`/`UIViewController`/`View`; move it to the appropriate unit.
- Blocking the main thread on network or disk.
- Hardcoded user-visible strings, colors, or dimensions.
- New third-party dependencies, analytics events, or permissions added as a side effect of a small subtask.
- `sleep`-based synchronization in tests.
- Catching platform exceptions broadly to suppress crashes rather than fix them.

Flavor-specific self-check additions:
- No new screen, route, permission, analytics event, or third-party dependency is introduced unless required by `acceptance_criteria.functional`.
- Every new asynchronous operation has a defined cancellation and error path that is exercised by a test.
- Every new interactive element has an accessibility label and a test asserting it.
- No user-visible string is hardcoded in code; all go through resources.
